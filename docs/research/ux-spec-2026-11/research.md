**Consolidated implication:** The strongest current direction is the Indexed workbench already labelled as a judgement in `concepts.md`: compact File/Edit/View/Project/Run/Libraries/Help commands, a bounded project index, one central sheet, one optional context drawer, and a status region. [DOC] [DOC `concepts.md` A0.5–A0.6] [JUDGEMENT]

The stage strip should explain `Modelled`, `You supplied this`, `Ready`, `Not run`, `Running`, `Failed`, `Not available yet`, and `Out of date`, but it should not become a second route through the same pages. [MAP] [MAP §D0, §E5, §F2] [JUDGEMENT]

The cost is persistent horizontal space and responsive focus management, while the rejected alternatives are a wizard-only application, a configurable panel shell, and a permanent pipeline canvas. [DOC] [DOC `concepts.md` Concepts 1–3] [JUDGEMENT]

### 6.1 Danish number parsing

Danish display uses a comma decimal separator and a period grouping separator according to [Unicode CLDR Danish data](https://www.unicode.org/cldr/charts/48/summary/da.html), while some European publication guidance uses spaces for grouped thousands. [STD] [STD CLDR, relevant number-symbol and pattern sections; [EU number-format guide](https://data.europa.eu/apps/data-visualisation-guide/number-formatting), whole, read 2026-11-16]

The parser should use one explicit project number format and a separately declared import format rather than guessing field by field. [JUDGEMENT]

| Mode and input | Proposed treatment | Reason | Evidence |
|---|---|---|---|
| Danish display | Render `1.234,56`; while editing, prefer ungrouped `1234,56`. | Grouping should not obstruct caret editing or error correction. | [STD] [STD CLDR] [JUDGEMENT] |
| Danish entry `1234,56` | Accept as 1234.56. | The decimal comma is unambiguous in declared Danish mode. | [STD] [STD CLDR] [JUDGEMENT] |
| Danish entry `1.234,56`, `1 234,56`, or non-breaking-space equivalent | Accept after validating grouping. | Period and spaces are recognized display traditions, but grouping positions must be valid. | [STD] [STD CLDR/EU guide] [JUDGEMENT] |
| Danish entry `1,234.56` | Reject with an example and a link to switch format. | Mixed international separators should not be guessed. | [JUDGEMENT] |
| International display/entry | Apply the inverse decimal/grouping rule and reject mixed Danish punctuation. | One declared grammar prevents different fields from parsing the same text differently. | [JUDGEMENT] |
| Clipboard or uploaded series | Require a source number format and unit at mapping; preview parsed samples and all errors. | Spreadsheet data may not match the project locale. | [TOOL] [TOOL Power Query/Tableau Prep manuals, whole] [JUDGEMENT] |
| JSON and Python boundary | Store JSON numbers, retain the original invalid string only as UI error state, and let Python parse/convert authoritatively. | The dumb-form architecture forbids a second JavaScript calculation or default implementation. | [MAP] [MAP §0.4.1–5] |

### 11.1 Clear no-radar recommendation

EV Scope should prohibit radar charts for bids, scenarios, strategies, and every other current result because normalized spokes hide absolute values and limits, axis order changes the shape, polygon area implies a composite score, and overlapping bids depend heavily on color. [GUIDE] [GUIDE Few radar critique; IBM Off the Radar] [JUDGEMENT]

IBM’s controlled study found radar weakest among the radial forms it tested, but it did not compare radar directly with tables or aligned bars, so the recommendation also depends on task fit and common-scale perception evidence. [GUIDE] [GUIDE IBM Off the Radar, full abstract/experiment summary; Cleveland–McGill, part] [JUDGEMENT]

The FT vocabulary’s inclusion of radar is a catalogue entry rather than efficacy evidence for auditable procurement, so it does not outweigh the comparison task’s need for raw values, limits, margins, units, source status, and model maturity. [GUIDE] [GUIDE FT taxonomy, whole] [JUDGEMENT]

The replacement is a semantic criterion-by-bid table with raw value, unit, requirement, status, signed margin, source, and model status, optionally supported by aligned dots or stripped bullets. [JUDGEMENT]

A weighted score may appear only when the procurement method itself defines and exposes the weights and formula. [MAP] [MAP §D12] [JUDGEMENT]

## 15. Numbered design principles for later specifications

Later UX documents should cite these stable IDs, such as `DP-07`, instead of restating or silently changing the research rationale. [JUDGEMENT]

1. **DP-01 — Separate commands from destinations:** Menus and command search hold verbs, while the project index holds named places and objects. [TOOL] [TOOL QGIS/OpenStudio/SAM manuals and source] [JUDGEMENT]
2. **DP-02 — Keep one primary navigation system:** Stage state explains dependency and availability but does not duplicate the project index. [MAP] [MAP §D0] [JUDGEMENT]
3. **DP-03 — Keep project identity and state visible:** Project name, audience view, save state, Check, Run, and result freshness remain visible in the application frame. [TOOL] [TOOL Figma/QGIS/VECTO manuals] [JUDGEMENT]
4. **DP-04 — Separate draft, version, scenario, and run:** Autosave protects the draft, Save synchronizes it, a scenario changes the base non-destructively, and a run freezes calculation evidence. [MAP] [MAP §D13, §F2] [JUDGEMENT]
5. **DP-05 — Make recovery non-destructive:** Restore, import migration, and conflict handling preserve the superseded state and explain what changed. [TOOL] [TOOL Figma/Grafana/QGIS manuals] [JUDGEMENT]
6. **DP-06 — Treat every import as a checked transaction:** Choose, parse, map, validate all rows, review impact, confirm, and account for accepted, changed, ignored, and rejected content. [TOOL] [TOOL Power Query/Tableau Prep/Linear/Airtable manuals] [JUDGEMENT]
7. **DP-07 — Make stage-entry contracts first-class:** Modelled, supplied, ready, not run, failed, unavailable, and stale remain distinct throughout inputs, runs, results, and exports. [MAP] [MAP §D0, §F2] [JUDGEMENT]
8. **DP-08 — Never silently discard typed or imported data:** A closed branch remains recoverable and visibly inactive while only active data reaches Python. [MAP] [MAP §0.4.7, Part E] [JUDGEMENT]
9. **DP-09 — Organise reusable things as objects and each sheet as a task:** Vehicles, routes, schedules, chargers, and profiles are shared objects; their fields follow user questions rather than engine order. [MAP] [MAP §1, §D14] [JUDGEMENT]
10. **DP-10 — Limit progressive disclosure to two practical levels:** Required and frequent content stays visible, while rare coherent detail gets one named level with status and issue count. [GUIDE] [GUIDE NN/g progressive disclosure] [JUDGEMENT]
11. **DP-11 — Keep core work out of drawers and dialogs:** Context panels hold checks, source detail, or help; modals hold short blocking decisions. [GUIDE] [GUIDE Carbon/NN/g] [JUDGEMENT]
12. **DP-12 — Match controls to consequence and precision:** Exact engineering values are typeable, important branches are visible, long libraries are searchable, and toggles are only immediate preferences. [GUIDE] [GUIDE GOV.UK/Carbon/Material/Apple] [JUDGEMENT]
13. **DP-13 — Make locale and units explicit:** Python owns parsing and conversion, Danish and international grammars are declared, ambiguous separators are rejected, and JSON stays locale-neutral. [MAP] [MAP §0.4.4–5] [STD] [STD CLDR] [JUDGEMENT]
14. **DP-14 — Make exact data table-first:** Tables own repeated inputs, audit records, sessions, months, and bids; visual views remain synchronized and optional. [MAP] [MAP §B3, §D5–D13] [GUIDE] [GUIDE UK tables] [JUDGEMENT]
15. **DP-15 — Give every visual an equivalent path:** Maps have ordered lists, calendars have exception tables, profiles have point tables, and charts have summaries and backing data. [STD] [STD WCAG 2.1.1, W3C complex images] [JUDGEMENT]
16. **DP-16 — Separate value state from source origin:** One compact field mark summarizes, while a drawer and ledger preserve source, edit, evidence, branch, and run-use dimensions. [MAP] [MAP §0.3–0.4, §F2] [JUDGEMENT]
17. **DP-17 — Freeze provenance with every run:** Preserve the active values, sources, transformations, start point, model/engine versions, fingerprint, warnings, and artifacts. [MAP] [MAP §F2] [TOOL] [TOOL VECTO/QGIS/PVsyst patterns] [JUDGEMENT]
18. **DP-18 — Budget visual emphasis:** One decision dominates, its limiting evidence follows, one primary visual answers the question, and detail recedes without becoming inaccessible. [GUIDE] [GUIDE UK dashboard/NN/g hierarchy] [JUDGEMENT]
19. **DP-19 — Choose charts by question:** Use position and length for comparison, lines for time, defined bands for uncertainty, Sankey for one conserved flow, and no chart when a number or table answers better. [GUIDE] [GUIDE Cleveland–McGill/FT/UK] [JUDGEMENT]
20. **DP-20 — Do not use radar charts:** Bid and scenario decisions require aligned raw values, limits, margins, sources, and status rather than normalized polygon area. [GUIDE] [GUIDE Few/IBM] [JUDGEMENT]
21. **DP-21 — Make every empty or partial state truthful:** Planned, not run, skipped, failed, stale, partial, and loading states never appear as zero, blank, or generic gray. [MAP] [MAP §F2] [STD] [STD WCAG 1.4.1] [JUDGEMENT]
22. **DP-22 — Put help and correction where work occurs:** Consistent Help, optional page guidance, linked error summaries, and inline messages preserve user effort. [STD] [STD WCAG 3.2.6, 3.3.1] [GUIDE] [GUIDE GOV.UK/NN/g] [JUDGEMENT]
23. **DP-23 — Design accessibility as a complete-process contract:** Keyboard, focus, reflow, target size, contrast, status messages, alternatives, zoom, and assistive technology are release criteria. [STD] [STD WCAG 2.2 AA] [JUDGEMENT]
24. **DP-24 — Recompose rather than squeeze on narrow screens:** Dense grids and side panels become record lists and full-screen forms while exact review remains available. [GUIDE] [GUIDE NN/g mobile tables] [JUDGEMENT]
25. **DP-25 — Show planned capability honestly:** Stable homes may explain future stages, but they never fabricate results or imply a committed answer to an open model choice. [MAP] [MAP Part D, §G2–G4] [JUDGEMENT] [OPEN]
